## 1. Key design decisions (recorded with rationale)

D1. **Temporal split (Stage A).** Calendar-date chronological split applied to matches (deliveries stay with their match): TRAIN = match_date <= 2024-12-31, VALIDATION = 2025-01-01 to 2025-12-31, TEST = match_date >= 2026-01-01. Boundaries are written into `config/phase4_split_v1.json` and `phase4_temporal_validation_plan.md` BEFORE any evaluation code runs, with the count of matches and pressure deliveries per format/role/period computed from dates only (no outcomes). Rationale: IPL seasons align with calendar years (train 2022-24, validate 2025, test IPL 2026); T20I has a similar volume per year; the 2026 test period has about 74 IPL and 70 T20I matches. The T20I train share (278 matches) is adequate for batters but the chase|q0.9 pressure sample for T20I bowlers is small (Phase 3 full-sample eligible T20I bowlers = 32); chunk 1 reports per format/role whether train/validation/test sizes support a meaningful split and records "limited" where they do not (documented limitation, not an invented split). Add a **rolling-origin** secondary scheme (origins 2024-01-01 and 2025-01-01 with the subsequent year as the evaluation fold) for the temporal-stability measure only; the primary lock remains TRAIN/VALIDATION/TEST. Alternative considered and rejected: random match split (violates chronology).
D2. **Test-period lock.** `TestLock` object in `app/phase4/split.py`: all data accessors that return TEST-period outcome columns (`runs`, `wicket`, residuals, balls with outcomes) go through `LockedFrame`; reading raises `TestPeriodLockError` and appends an entry to `data/reports/phase4_lock_log.json` (deterministic text, no timestamps except a counter) unless `evaluate_on_test(...)` (the single named final-evaluation function) has opened the lock. Pre-delivery state columns for test matches (no outcomes) remain accessible for baseline-feature construction because they depend only on prior information. All selection (definition, shrinkage strength, eligibility thresholds, baseline variant) is computed before the lock opens and written to `data/reports/phase4_frozen_choices.json` (with SHA-256 of the file recorded in the evaluation output). The final evaluation function refuses to run if the frozen-choices file is missing or was modified after its recorded hash.
D3. **Strictly prior par.** Par for a match uses only first-innings source innings from matches with `match_date` strictly before the evaluated match date (same-day matches excluded, even in earlier-sorted rows; documented as conservative), same competition_type as the evaluated match, cell fallback chain as in `pressure_features` (E0 to E1 to E2 to NONE). If fewer than `min_prior_innings` (30, existing rule; sensitivity 15/60) prior source innings exist for the cell, fall back to the next coarser level; if all fail the value is NULL and `par_unavailable_insufficient_prior = True`; never zero-filled. The existing `par_runs_prior` is checked for these exact semantics first (the existing column is the base; if its same-day rule differs, re-implement the date-strict rule in `app/phase4/par.py` and prove equivalence with a test). Computation is vectorised by sorting source innings by date and using cumulative aggregates per cell on unique dates (`searchsorted` with side=left on the date so same-day rows are excluded), avoiding an O(n^2) loop. LOMO par stays only in the retrospective descriptive table, labelled `DESCRIPTIVE_ONLY_USES_FUTURE_MATCHES`, and `LeakageGuard` raises if a LOMO column is requested by the scoring pipeline.
D4. **Baseline in the temporal setting (Stage B).** Primary = TRAIN-FROZEN parameters: the empirical-Bayes cell means and shrinkage `k` from `baseline_engine` are fitted on TRAIN deliveries only and applied unchanged to VALIDATION and TEST deliveries (Normalization/shrinkage parameters use training only). Secondary comparator = EXPANDING strictly-prior baseline refitted at each season boundary (rolling origin) to measure stability. Alternatives reported in Stage D: with/without season offsets, coarser (L1/L2) vs finer (L0) cells, leave-match-out vs strictly prior. The per-delivery expected values for TEST rows come from TRAIN parameters only, so no test outcome touches them. Unseen cells in later periods fall back down the existing L0 to L3 chain; fallback counts are reported.
D5. **Shrinkage estimator.** Normal-normal empirical Bayes per (role, format, stream), TRAIN-period data only: player residual mean `r_i` with per-player noise variance `s_i^2/n_eff_i` (n_eff by Kish over matches; `s_i^2` from the player's own within-match variance, with a pooled variance fallback for players with fewer than 3 matches, via bootstrap-by-match as a check), pooled mean `mu_{-i}` over OTHER players only (leave-one-player-out via `shrinkage.pooled_other_mean`), between-player variance `tau2` by method of moments on TRAIN with floor `tau2_floor` (reuse `k_from_children`, default 0.01 for continuous streams; floor-hit flagged `shrinkage_floor_hit`). Estimate = `mu_{-i} + B_i (r_i - mu_{-i})` with `B_i = tau2 / (tau2 + s_i^2/n_eff_i)`. Config set: `shrink_none` (B=1, kept as sensitivity), `shrink_primary` (EB as above, chosen on VALIDATION by the rule in D6 and frozen), `shrink_tau0.5`, `shrink_tau2`, `shrink_tau4` (tau2 multipliers), and `shrink_target0` (target 0, kept as named sensitivity from residual finding 1). Batter and bowler populations are separate; IPL and T20I populations are separate; combining happens after shrinking each format. Players' own data is never in their own pooled mean. Assumptions (normality, independence of matches, exchangeability of players within format/role, homoscedastic within-player noise after n_eff) are written into `phase4_shrinkage_sensitivity.md`. Hand-checkable test cases are listed in section 5.
D6. **Definition-comparison rule written BEFORE test (Stage D).** The selection rule is committed to `config/phase4_definition_rule_v1.json` and quoted in `phase4_definition_comparison.md`, and uses only TRAIN and VALIDATION data. Metrics on the nine full-eligibility candidates (chase/inn1/any x q 0.75, 0.90, 0.95; names verified against `pressure_eligibility_rules_v1.json`): (a) pressure discrimination: mean residual and standardised difference of pressure rows vs non-pressure rows, and Pr(dismissal), dot, boundary differences, with match-cluster bootstrap CI; (b) performance relative to baseline (mean residual in pressure sample, by role/format); (c) player differentiation: split-half reliability by match (odd/even matches within TRAIN), Spearman-Brown corrected, plus ICC/signal-to-noise `tau2 / mean(s_i^2/n_eff)`; (d) temporal stability: correlation of player residuals TRAIN vs VALIDATION among players with enough balls in both; (e) format differences (IPL vs T20I effect sizes, report only); (f) eligible population; (g) sample sufficiency; (h) ranking stability (bootstrap Top-10 inclusion, reported); (i) threshold sensitivity. Rule: rank candidates by a pre-declared lexicographic gate. Gate 1 requires a minimum number of eligible players per format/role (none lower than half the best candidate so no near-empty pools win; cannot be satisfied just by population: this is a floor, not an objective). Gate 2 selects by the pooled (batter+bowler, both formats) split-half reliability and TRAIN-to-VALIDATION stability (equal weight, average of the two), higher is better; ties within 0.02 go to the candidate with greater discrimination effect; only then to the larger population. Max eligible population is never the selector. The result is "one of N=9 examined, PROVISIONAL" and may or may not confirm `chase|q0.9`; report the actual winner even if it differs, and carry the leading candidate `chase|q0.9` as the labelled default only if it is not rejected by Gate 1. Multiplicity is stated.
D7. **Eligibility thresholds (Decision 5).** Re-derive per (format x role): IPL batter, IPL bowler, T20I batter, T20I bowler, separately, from TRAIN-period pressure-sample distributions of pressure balls and distinct matches: percentile candidates (P10, P25, P50, P60, P75 of per-player pressure balls) plus practical rungs (reuse `confidence_engine.percentile_candidates`, `practical_candidates`, `build_ladder`). Each candidate threshold is scored on pressure opportunities, distinct matches, n_eff, estimation uncertainty (median shrunk-estimate interval width), bootstrap stability (match-cluster, 1,000 resamples, seed from config), ranking stability (Top-10 inclusion for pool), and temporal reproducibility (does a player eligible in TRAIN remain eligible in VALIDATION; correlation across periods). Selection of each threshold is frozen from TRAIN+VALIDATION before test. Phase 3 T20I placeholders (batter 24, bowler 36 balls) are labelled as superseded placeholders in the output. Fewer than ten eligible is reported as is; never lower a threshold to reach ten.
D8. **Format weights (Decision 6).** After Stage B/C, re-run all eight configs (`config/format_weights_v1.json`: w100_0, w85_15, w80_20, w70_30, w60_40, w55_45, w50_50, w0_100) over the SAME frozen eligibility rules, via `pressure_format_sensitivity.run`/`format_weight_report` logic, but over the new scores. Report IPL-only, T20I-only, combined (only for players eligible in both formats; missing format never zero-filled), Top-10 overlap (marked "trivially full" when the pool is at most 10), Spearman, rank movement, bootstrap stability. Report definition sensitivity and weight sensitivity in separate tables and files, no joint grid, no winner selected; 70:30 stays `PROVISIONAL_NOT_VALIDATED`.
D9. **Phase hardening (Decision 4).** `phase_engine.phase_bounds(limit)` uses `pp_end = (3*L)//10`, `death_start = ceil(3*L/4)` (L=120 gives 36 and 90). Chunk 1 documents exact boundaries for every innings limit L actually present in the data (the set is read from `deliveries`/`matches` revised overs: expected 120 plus shortened values such as 60, 66, 72, 84, 90, 96, 100, 108; confirm from the data), hand-checks several in tests, reports affected deliveries and innings, and states the revision-timing caveat: the revised limit becomes known only when the revision is announced (mid-innings for innings 1 revisions), so phase labels for balls before the announcement could use a later-known L; the report counts such innings (those where `first_inn_revised_overs` or `second_inn_revised_overs` differs from 120) and offers the conservative sensitivity of excluding them from phase-dependent metrics. DLS rows whose resources and revised state cannot be reconstructed stay excluded (3,404 rows; 0 in the primary chase sample) via existing `RULE_DLS_*` restrictions; resources are never imputed. All original delivery records are preserved (exclusions are masks, not deletes); a test checks row counts unchanged.
D10. **Classification (additional requirement).** Independent fields: `nationality` in {Indian, Overseas, Unknown}, `international_status` in {Capped, Uncapped, Unknown}, per-field `*_verification` in {VERIFIED_FROM_SOURCE, DERIVED, UNVERIFIED} (derived capped carries sub-label `DERIVED_FROM_OFFICIAL_T20I_APPEARANCES`), per-field `*_source`. All four nationality x status combinations supported; no implication either way. Manual overrides: `config/classification_overrides_v1.csv` (columns `player_id, field, value, source, verified_by, verified_date`), header only by default, validated on load (known player_id, field in the two fields, value in the enum, non-empty source/verified_by, ISO date, no duplicate (player_id, field)); override wins and is labelled `VERIFIED_FROM_SOURCE` with source `MANUAL_OVERRIDE:<source>`. Never pre-populated.
D11. **Composition optimiser.** Constraints per group g in {IN_CAPPED, IN_UNCAPPED, OS_CAPPED, OS_UNCAPPED, UNKNOWN} (each player belongs to exactly one group; Unknown nationality OR Unknown status falls in UNKNOWN unless the config says to split) with independent exact/min/max, total size N (default 10), optional role min/max. Method: exact DP over groups (grouped knapsack; group counts bounded by N), pick top-k scores within each group (sorted by score desc, player_id asc), DP maximises total score with deterministic tie-break (lexicographic on selected player_id tuple). Feasibility is checked first; infeasible requests return the failing constraint and available counts. Role lists are handled by a second layer only if roles are requested (small ILP-by-DP over group x role count lattice; if too large the service refuses with an explicit message). Optimality is proven on small constructed tests by brute-force enumeration over all subsets. Alternative considered: scipy `milp`; rejected to keep the result deterministic and dependency-light.
D12. **API gating.** `app/main.py` creates the FastAPI app, router prefix `/api/v1`. Rankings/selection/profile endpoints read only the `p4_*` experimental tables from the exploratory store opened `read_only=True`; every response includes `status="EXPERIMENTAL_NOT_VALIDATED"`, `official_ranking=false`, `disclaimer`; any request with `official=true` or publication intent returns 403 with error code `OFFICIAL_RANKING_NOT_AUTHORIZED`. Admin endpoints (override reload, rebuild classification) require header `X-Admin-Token` compared in constant time against `SUPERR_ADMIN_TOKEN` env (absent means admin disabled, 503). No endpoint accepts a filesystem path or raw SQL; sort fields are enum-whitelisted; pagination `limit<=200`, `offset>=0`. Open decision O2: the admin mechanism is a minimal token because the repo has no auth system.

## 3. Data flow and tables (all in `data/database/exploratory.duckdb`, prefix `p4_`, status column `EXPERIMENTAL_NOT_VALIDATED`)

Flow: official `superr.duckdb` (read-only) to `load_state` (reuse `exp_pre_delivery_state`/`exp_pressure_signals`, rebuilt in memory if stale per manifest hash) to `data.py` (attach match_date, competition_type, period; apply restriction masks) to `par.py` (strictly prior) to `baseline.py` (train-frozen expected values) to `scoring.py` (pressure sample by definition, residuals, LPO shrinkage, bootstrap) to `definitions.py`/`eligibility.py`/`formatweights.py`/`stability.py` (selections frozen in `phase4_frozen_choices.json` before `evaluate_on_test`) to `reports.py`. In parallel: players + squad CSV + match_squads to `classification.py` to `selection.py`/`profiles.py`/API.

## 6. Risks and mitigations
R1. Strictly prior par shrinks the usable early sample: TRAIN matches from early 2022 have few prior innings, so many 2022 deliveries get `par_unavailable_insufficient_prior`. Mitigate: fallback chain, counts reported, par-dependent signals excluded for those rows rather than zero-filled; chase pressure (`req_to_exp`, RRR) is less par-dependent than `inn1` definitions, so candidate comparison must report par availability per candidate.
R2. Pressure sample sizes after a three-way split are small, especially T20I bowlers (Phase 3 full sample 32 eligible; train alone smaller). Likely outcome: very few or zero eligible in TRAIN/VALIDATION/TEST for some cells; report honestly; evaluation uses pooled TRAIN+VALIDATION for estimation with TEST as an out-of-sample check, and rolling-origin for stability. Do not relax thresholds.
R3. Date oddity: T20I matches dated up to 2026-11-01 with deliveries; the TEST period would include these. Treat dates as given, flag in the DQ report, offer a sensitivity (TEST limited to dates up to the IPL 2026 end, 2026-05-31) rather than altering data. Raise as open question O3.
R4. Compute cost: bootstrap by match with 1,000 resamples across 9 definitions x 2 formats x 2 roles x threshold/shrinkage grids may be slow; use vectorised per-match aggregation (player x match matrices), fixed seeds, cache aggregates; target the orchestrator under about 30 minutes; allow `--fast` only for tests, never for reported numbers.
R5. Selection-rule circularity and multiplicity: the rule is pre-registered (hash recorded) and the winner is "one of nine"; ranking stability and temporal stability both appear in the rule, so ensure the rule does not use test outcomes. A reviewer should check config hash timestamps (hash recorded in `phase4_frozen_choices.json`).
R6. Classification will be mostly Unknown; uncapped lists and presets will be empty or tiny. This is the correct honest result. Risk: reviewer or user expecting populated uncapped lists. Mitigate with explicit coverage tables and data request.
R7. No existing API scaffold: chunk 4 is large (classification + optimiser + profiles + API + docs). If the loop budget is a concern, order within chunk 4 is: classification, optimiser, uncapped rankings, API list/ranking/selection endpoints, profile endpoint, docs.
R8. Name-based resolution can create wrong merges (Rashid Khan, Abdul Samad ambiguous). Rule: ambiguity gives Unknown + unresolved list; tests prove no name-only merge.
R9. Windows/PowerShell: set `$env:PYTHONUTF8=1`; avoid multi-line `python -c` in PowerShell (use script files); do not leave uvicorn running.
R10. Existing tests assume store tables not modified; Phase 4 writes only `p4_*` tables (test T15 enforces). DuckDB file locking: close connections before another process opens read-write.
