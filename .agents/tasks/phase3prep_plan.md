## 4. Design decisions (made; open alternatives listed in section 6)

1. Ordering and counters: order by `(match_id, innings_number, innings_ball_num)`. Verify first that `innings_ball_num` is contiguous 1..n per innings and monotone with `source_row_no`; fail the build otherwise. All "before" values use exclusive cumulative sums (cumsum minus current row) within `(match_id, innings_number)`; do not use `shift` across group boundaries.
2. State columns (all pre-delivery): lineage `match_id, innings_number, innings_ball_num, source_row_no`; context `competition_type, comp_id, season_key, match_date, venue_id, knock_out, stage, batting_team_id, bowling_team_id, striker_id, non_striker_id, bowler_id, chase_flag`; delivery facts used only as labels, kept in a clearly separate column group prefixed `out_` (`out_batter_runs, out_is_wicket, out_wicket_credited_to_bowler, out_charged_runs, out_is_boundary, out_is_dot, out_extras_type`): these are outcome columns, never inputs to state features; availability matrix marks them "label only". State: `team_runs_before` (batter runs plus primary plus secondary extras, i.e. the `source_total_runs` definition; flag secondary as RULE_EXTRAS_SECONDARY unverified split but the total is used for score), `team_wickets_before`, `wickets_remaining`, `legal_balls_before`, `overs_limit_balls`, `overs_limit_source` (`DEFAULT_120`, `REVISED_OWN_INNINGS`, `CARRIED_FROM_FIRST_INNINGS_UNVERIFIED`), `legal_balls_remaining`, `legal_over_1based`, `ball_in_legal_over`, `phase`, `crr` (NULL when `legal_balls_before = 0`), `target`, `target_source` (`NONE_FIRST_INNINGS`, `INN1_TOTAL_PLUS_1`, `REVISED_TARGET`, `NO_INNINGS_1_TARGET`), `runs_required`, `rrr` (NULL when balls remaining is 0 or no target), `rrr_minus_crr`, `required_run_gap` (`runs_required - par_remaining`), `par_*` (section 5), `batter_balls_faced_before`, `batter_runs_before`, `bowler_legal_balls_before`, `bowler_overs_completed_before`, `bowler_runs_before`, `bowler_wickets_before`, `non_striker_id`, `is_legal_ball`, `legal_increment`, `counts_as_ball_faced`, `extras_label_unverified`, `extras_runs_with_none_type`, `wicket_flag_anomaly`, `penalty_row_flag`, `dls_flag`, `dls_revised_target`, `dls_revised_balls_own`, `resource_status` = 'NOT_RECONSTRUCTED' for every DLS-flagged row (never invent the DLS table), `dls_state_reliable`, `restricted_innings_flag`, `restriction_reason_code` (`CONFIRMED_SUPER_OVER_BY_CRICSHEET` | `UNVERIFIED_INNINGS_ROLE` | NULL), `cricsheet_total_flag` (the ten innings of RULE_CRICSHEET_TOTALS), `state_version`, `build_id`. Partnership info is omitted (optional in the brief; no restriction needs it).
3. Innings-2 target: `revised_target` if not null (RULE_DLS_TARGETS requires revised fields), else innings-1 `source_total_runs + 1`. The innings-1 total is computed from innings-1 rows and attached only to innings-2 rows (target is known once innings 1 completes), never to innings-1 rows. A match with innings 2 but no innings-1 rows gets `target_source = NO_INNINGS_1_TARGET`, target NULL. Cross-check report: target vs `innings.source_total_runs + 1` for all 845 chases (820 plain, 23 revised, plus the 2 carried-overs cases), the 8 revised targets that equal total+1, and the 15 that differ.
4. Overs limit: innings limit = revised value of its own innings when not null, else 120. For innings 2 when `second_inn_revised_overs` is NULL but `first_inn_revised_overs` is not (16753, 19959, and the NO_RESULT matches with innings 2 absent): set limit to the first-innings value only as `CARRIED_FROM_FIRST_INNINGS_UNVERIFIED`, set `dls_state_reliable = false`, and exclude those rows from chase-pressure populations (kept in the table; reported as sensitivity). Mid-innings interruption timing is not in the data, so the limit is applied from ball 1 (documented limitation, row flag `limit_applied_from_start_assumed`). Any innings whose legal balls exceed its limit fails the build.
5. Phases (configurable in `config/pressure_rules_v1.json`): legal over 1-6 powerplay, 7-15 middle, 16-20 death for limit 120 (verified by over counts). For limit L < 120: proportional boundaries `pp_end = floor(0.30*L)`, `death_start = ceil(0.75*L)` in legal balls (0.30 and 0.75 are 36/120 and 90/120). This is a documented proxy for the ICC reduced-over powerplay table, listed as an open decision. Phase label stored with `phase_rule` (`FULL_120`, `PROPORTIONAL_DLS`).
6. Counting definitions (single source in `cricket_calculations`): `counts_as_ball_faced` = striker not null AND extras_type not in (wide, Penalty) for innings 1/2 (identical to `BATTER_SQL`; a test compares row counts per batter against `BATTER_SQL`); `legal_increment` as in section 1; bowler legal balls = `is_legal_ball` and not Penalty; bowler charged runs and wicket credit as `proxy_samples`; team wickets from `is_wicket` (with variant using `dismissed_player_id` for RULE_DISMISSED_NO_FLAG).
7. Innings 3/4: rows stay in the state table with `restricted_innings_flag = true`; their state columns are computed with the same function but `phase`, pressure flags and all pressure-sample inclusion are null/false; reason codes per section 1. Pressure and baseline code selects `NOT restricted_innings_flag` through the RestrictionApplier, never by an ad hoc filter.
8. Leakage control for par: leave-one-match-out (LOMO) cross-fitting from official data only, within `competition_type`, innings 1 and 2 pooled or separate (decide from the data; document). Cells: `par_runs_at_ball(competition_type, innings, legal_balls_before)` mean cumulative runs, and `expected_remaining_runs(competition_type, legal_balls_remaining, wickets_remaining)` mean runs scored from that state to the end of the innings, estimated with the row's own match removed (sum minus own contribution divided by count minus own count). Sparse cells fall back to a coarser parent (balls bins of 6, wickets bins) with empirical-Bayes shrinkage using `eb_shrink`. A strictly-prior-matches variant is documented for the validation phase but not built. Test: changing any row of match M (including its final total and result) does not change any par/state value of match M (but may change other matches).
9. Pressure signals (Stage 3 inputs; no cutoff chosen in code): chase: `rrr`, `runs_required`, `legal_balls_remaining`, `wickets_remaining`, `rrr_minus_crr`, `required_to_expected_ratio = runs_required / expected_remaining_runs` (LOMO), `resource_ratio = legal_balls_remaining * wickets_remaining / limit / 10`, knockout flag; innings 1: `par_deviation = team_runs_before - par_runs_at_ball`, `projected_total_gap = team_runs_before + expected_remaining_runs - par_total`, `wickets_remaining`, phase, knockout flag. Absolute pressure = raw signal value compared with whole-population quantiles; relative pressure = percentile rank within the same (competition_type, phase, wickets bin) cell. Candidate thresholds = signal quantiles from the observed distribution at a grid in config (e.g. p50, p75, p80, p90, p95; the grid is a search grid, not a chosen cutoff).
10. Baseline (Stage 4): hierarchical stratified empirical-Bayes, no model fitting. Hierarchy for expected outcomes: L0 `competition_type x phase x wickets_bin x pressure_band` -> L1 drop pressure_band -> L2 `competition_type x phase` -> L3 `competition_type` -> L4 pooled. Binary outcomes (dot, boundary, wicket): beta-binomial shrinkage toward the parent cell; runs and charged runs: normal EB (`eb_shrink` style, between-cell variance by method of moments); pseudo-count k per level from the data. Expected value for a delivery of player p is computed leave-player-out (cell sums minus p's own contribution in that cell) so a player's own results do not set their own expectation. Wickets bins: `wickets_remaining` 10-8, 7-6, 5-4, 3-1 (confirm sample sizes first). Primary baseline B = pressure-band-stratified (the player is compared with peers in the same pressure band, so death-over and ordinary-over rates are never compared raw); sensitivity baseline A = context-only (pressure band removed) so the player's pressure effect is included. Competition/season and venue run environment: computed as LOMO shrunk run-rate ratio, default OFF in the primary baseline and reported as a sensitivity (venue/season sample sizes decide whether supportable); otherwise recorded as "not used". Calibration identity: within every L0 cell, sum(actual) equals sum(expected) for the pooled (non-leave-player-out) baseline to numerical tolerance, and for leave-player-out the total over all deliveries differs only by a reported small amount. Uncertainty: bootstrap by match (stratified by format), seed 20260512, resample count configurable (default 500 for baseline; 1000 for eligibility as in Phase 2.5), baseline held fixed inside the bootstrap (stated limitation; a refit-inside variant is listed as an option). Model options considered and rejected for now: regularised logistic and gradient boosting expected-outcome models (documented in `baseline_methodology_v1.md` with a temporal-holdout calibration plan).
11. Pressure-specific eligibility (Stage 5): build `ProxySamples`-shaped per (format, player, match) sufficient statistics from pressure deliveries: batter streams `n` (pressure balls faced), `ave_runs` actual minus expected runs sums and sums of squares; bowler streams `n` (pressure deliveries), `legal_balls`, `ave_charged`, `ave_wkt`. The score for stability is the shrunk mean actual-minus-expected (batter: runs per ball; bowler: `-z(charged AvE) + z(wicket AvE)` as in Phase 2.5, equal weights, labelled arbitrary). Per candidate pressure definition x format x role: distributions (reuse `distribution_for`), percentile candidates P10/P25/P50/P75 plus nominal practical ladders scaled for pressure sample sizes (kept only between observed p10 and p90, as in Phase 2.5), single-measure and conjunction rules, eligible counts, pressure deliveries, distinct matches covered, n_eff, Top 10 overlap and Spearman between neighbouring thresholds, bootstrap-by-match CI widths, pool verdict (reuse `pool_verdict`; fewer than ten eligible is stated and never padded). Comparison table: how many players pass the Phase 2.5 all-situation thresholds (read from `data/reports/eligibility_threshold_experiment.json` recommendation) when counted on pressure samples, versus the pressure-specific thresholds. The provisional recommendation is written only after reading the actual output.
12. Format-weight rerun (Stage 6): eight configs from `config/format_weights_v1.json` (hash and id on every result), pressure tables injected into `normalization_engine`; combined only when both formats ELIGIBLE; single-format players in their own lists; ADJUSTED_ESTIMATE separate; report IPL-only, T20I-only, combined, overlap, Spearman, movement, eligible-population change per config; outputs `pressure_format_weight_sensitivity.json/.md` titled EXPLORATORY. Phase 2.5 note: 100:0 and 0:100 produce the same combined population as every other config; keep that and say so. If fewer than ten players are combined-eligible under pressure, report the short list and the single-format lists; do not lower thresholds to fill.
13. Restrictions (Stage 7): see chunk D. Official records and original files are never modified; verify by `snapshot_from_settings` before/after every script and by the orchestrator.

## 6. Open design questions (default chosen; record in the spec as user decisions)

1. First-innings par: default = LOMO empirical par curve and expected remaining runs by `(competition_type, legal balls remaining, wickets remaining)`. Alternatives: strictly prior matches only (temporal), venue-adjusted par, DLS-style resource table (not reconstructed). Different choices change innings-1 pressure labels.
2. DLS phases and limits: proportional 0.30/0.75 scaling and "limit applied from ball 1". Alternatives: ICC powerplay table by reduced overs; excluding all DLS-flagged rows from phase-based pressure. Mid-innings interruption timing is not in the data.
3. DLS matches without a stated innings-2 limit (16753, 19959): excluded from chase-pressure populations by default; alternative is carrying the first-innings limit as an assumption.
4. Revised "overs" columns are balls: inferred from the data (all multiples of 6, never exceeded by legal balls), not from documentation; confirm with the data owner.
5. Pressure thresholds: not chosen. Candidate quantile grid (p50, p75, p80, p90, p95) is a search grid; the provisional pick is made after reading Stage 3/5 output and flagged not validated. Absolute versus relative pressure as primary is open.
6. Primary baseline = pressure-band-stratified (B) versus context-only (A); venue/season environment default off.
7. Team wicket count uses `is_wicket` (Retire Out counts as a fall of wicket); alternative excludes retired-out. The 2 'None'-type rows with extras runs stay in totals and are flagged.
8. Score for eligibility stability is actual-vs-expected shrunk mean (batter) and equal-weight z combination (bowler), same arbitrariness as Phase 2.5; not a pressure score.

## 7. Risks

- `confidence_engine` coupling to fixed streams (refactor could break the 142 tests): keep the change additive; fallback subclass approach in section 2.
- Pressure samples are small: many (format, role, definition) cells may have fewer than ten eligible players, especially combined IPL and T20I; the reports must say so and never pad or impute.
- Runtime: state build and LOMO tables must stay vectorised (200,999 rows); bootstrap with baseline held fixed to keep it cheap; time-box and report if resample counts are reduced (`--n-boot`).
- Leakage subtleties: LOMO par uses other matches that happened later in time (acceptable for descriptive distributions, not for validation; stated). Innings-2 target is known to the chasing team only after innings 1; innings-1 rows must never see it. Do not put `out_` columns into any feature.
- Register `row_filter` strings are prose; the implementation table is the single executable interpretation and must be tested for completeness.
- DuckDB 2.0.0 quirks: DROP/CREATE inside the exploratory store only; read-only handles for the official DB; Windows file locks (close connections before hashing files).
- The 'Penalty' row has `is_legal_ball` TRUE in the DB; it must be excluded by rule, not by the stored flag.
- `overid`/`over_ball_num` are row counters; any code using them as legal over would misplace death-over rows (8,429 rows have `over_ball_num > 6`).
- Reports must not contain player names outside a labelled technical appendix and must not use ranking language.
- Do not run or write anything under the Cricsheet directories except through existing read-only validation outputs; Cricsheet never feeds a baseline or feature.
