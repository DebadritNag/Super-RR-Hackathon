### Proxy definitions (all PROXY_NOT_PRESSURE; innings 1 and 2 only; formats IPL and T20I; OTHER_T20 reported in the distribution file only)

Innings 3/4 are excluded from every proxy sample by an explicit per-metric restriction (issue `open_innings_3_4_role_unverified`), not deleted. Matches with NO_RESULT/ABANDONED status keep their innings 1/2 deliveries (no global match exclusion).
- Batter `balls_faced` = count of deliveries with `striker_id = p`, `extras_type <> 'wide'` and `extras_type <> 'Penalty'`. A no-ball (`Overstep`, and `other`, which behaves no-ball-like but whose label is unverified) is a ball faced but not a legal ball. Also report `legal_balls_faced` (`is_legal_ball`) for comparison. `balls_faced` is the batting sample-size measure for thresholds and the unit `n` for shrinkage.
- Batter value per ball `x = batter_runs`; `sum_x`, `sum_x2` per (player, match). `batting_proxy = 100 * shrunk runs per ball`. Dismissals are not in the proxy (kept simple; stated as a limitation). `innings_batted` = distinct (match, innings) with at least one ball faced; `matches` = distinct match.
- Bowler `legal_balls` = count of deliveries with `bowler_id = p` and `is_legal_ball`. `deliveries_bowled` = all deliveries by the bowler excluding `Penalty`. Runs charged to the bowler on a delivery = `batter_runs + (extras_primary_runs if extras_type in ('wide','Overstep','other') else 0)`; `extras_secondary_runs` and byes/legbyes/Penalty are not charged (split unverified, 36 rows). `spell` = distinct (match, innings) bowled in; `matches` = distinct match.
- Bowler economy value per delivery `x_e = runs charged`, unit `n = deliveries_bowled`; `econ_proxy = 6 * shrunk runs per delivery`. Wicket value per delivery `x_w = 1` if `is_wicket` and `dismissal_type` is bowler-credited (coder lists the actual distinct `dismissal_type` strings from the DB first; expected Caught, Bowled, LBW, Stump, Hit Wicket; excluded RunOut, Retire Out, Obstructing the field spellings), else 0; rows with `is_wicket` false are never counted even if `dismissed_player_id` is set (12 rows, restriction). `bowling_proxy = -z(econ_shrunk) + z(wicket_rate_shrunk)` with z computed over the format's players with at least one delivery; equal weights fixed and documented as arbitrary.
- Batters are z-scored within format the same way (`z(batting_proxy)` over the format's observed players) only when building combined scores; format-specific proxy scores remain on their own scale.

### Shrinkage and n_eff (`shrinkage.py`)

Per format and role, over all players with n >= 1 (independent of any threshold): P players, per-player n_p, sum_x_p, sum_x2_p, rate r_p = sum_x_p / n_p.
- `mu0 = sum(sum_x) / sum(n)`.
- Within variance `sigma2 = (sum(sum_x2) - sum(n_p * r_p^2)) / (sum(n) - P)`.
- Between variance (method of moments, DerSimonian-Laird form): `Q = sum(n_p (r_p - mu0)^2)`, `c = sum(n) - sum(n_p^2)/sum(n)`, `tau2 = max(1e-12, (Q - (P-1) sigma2) / c)`.
- Prior strength `k = sigma2 / tau2`; shrunk rate `r~_p = (n_p r_p + k mu0) / (n_p + k)`; posterior sd `sigma / sqrt(n_p + k)`.
- `n_eff_shrink_p = n_p^2 / (n_p + k)` (data weight B_p = n_p/(n_p+k) times n_p).
- `n_eff_kish_p = (sum_m n_pm)^2 / sum_m n_pm^2` over the player's matches (effective number of equally contributing matches).
Only sufficient statistics per (player, match) are needed, so the bootstrap works on those.

### Decision 2 procedure (`confidence_engine.py`, `scripts/run_eligibility_experiment.py`)

1. Distribution (`eligibility_distribution.json`): per format (IPL, T20I, OTHER_T20 separate) and role (batter, bowler) independently, for measures balls (batter `balls_faced`, bowler `legal_balls`), matches, innings/spells, `n_eff_shrink`, `n_eff_kish`: count observed, mean, std, min, p5, p10, p25, p50, p75, p90, p95, max, histogram (fixed bin edges per measure, stored), zero-inflation note (count with n <= 5, share with a single match). Window dates and match counts per format included.
2. Candidates: percentile candidates are `ceil` of the p10, p25, p50, p75 values of each measure over observed players of that format and role. Practical candidates come from the nominal ladder in `config/eligibility_rules_v1.json` (batter balls 30/60/120/180/240/300; bowler legal balls 24/48/96/144/192/240; matches 3/5/8/10/15/20; innings/spells 3/5/8/10/15/20; n_eff 20/40/80/120). The script reports every nominal value but marks as practical only those lying between the observed p10 and p90 of that measure and not within 5 percent of an existing percentile candidate; the report states each kept value with its observed percentile rank and eligible count (justification generated from numbers).
3. Rules evaluated: single-measure rules `measure >= T` for each candidate, plus conjunction rules (balls AND matches) built from practical candidates only (limited grid, max 12 pairs). Batter and bowler eligibility are computed independently (an all-rounder can be eligible in one list only). Combined eligibility = eligible in IPL under the IPL threshold AND in T20I under the T20I threshold; practical values are identical across formats, percentile values are format-specific; the ladder pairs candidates by label (P10, P25, P50, P75, PR1..).
4. Per threshold report: eligible count per format and combined; distinct match coverage (matches in window with at least one eligible player observation, count and percent of that format's matches with deliveries); sample-size distribution among eligible; Top 10 overlap and Spearman versus the adjacent ladder neighbours and versus the reference threshold (reference = lowest practical candidate of that measure, documented), with n; bootstrap; pool verdict.
5. Pool verdict rule (configurable): `eligible >= max(pool_min_absolute=30, pool_min_multiplier=3 * list_size=10)`; verdict states the count and whether fewer than ten would be eligible. Never pad to ten.
6. Bootstrap: resample unit = match, stratified by format, with replacement, 1000 resamples (`--n-boot`), seed 20260512 from config, per (format, role) streams via `numpy.random.SeedSequence(seed).spawn`. Each resample multiplies per-(player, match) sufficient statistics by the match multiplicity, re-estimates shrinkage, recomputes proxy scores for the original eligible set (eligibility itself is held fixed; its sampling variability is not modelled and is stated). Report per threshold: median and p95 of the 95 percent interval width (percentile interval 2.5 to 97.5) of the proxy score, mean Top 10 membership frequency of the original Top 10, number of players with frequency >= 0.5, expected Top 10 overlap between resample and original. Player-level intervals only in the proxy technical appendix for the reference threshold.
7. Recommendation (`recommendation_inputs` in the JSON, narrative generated from it): per format and role, the highest ladder threshold T that still has a sufficient pool, and the lowest T at which Spearman versus the next higher threshold >= 0.95 and Top 10 overlap >= 8 and median interval width has stopped falling by more than 10 percent per step. The coder reads the actual output first; if the generic rule contradicts the data, change the rule in config, rerun and document in the report. Result is labelled PROVISIONAL, with trade-offs (pool size versus noise versus match coverage), and states plainly when a list would have fewer than ten eligible players.

### Decision 1 procedure (`normalization_engine.py`, `format_weights_v1.json`)

- Config: `version`, `created_date`, `status: "PROVISIONAL"`, `rationale`, `default_config_id: "w70_30"`, `default_flag: "PROVISIONAL_NOT_VALIDATED"`, `configurations` = eight objects `{id, ipl_weight, t20i_weight}` for 100:0, 85:15, 80:20, 70:30, 60:40, 55:45, 50:50, 0:100. Load validates: exactly these eight ids unique, weights in [0,1], sum to 1 within 1e-9, default present and flagged provisional; invalid input raises `FormatConfigError`. Hash = sha256 of canonical JSON (sorted keys, compact separators). Consistency check against `Settings.ipl_weight/t20i_weight` returns a warning entry in the output (never raises, never alters Settings).
- Eligibility for the sensitivity run uses a data-driven placeholder that does not depend on weights: the P25 rule per format and role (balls measure), recomputed from the data; the same experiment is repeated at P10 and P50 as robustness (`eligibility_level` recorded). This avoids circularity with Decision 2.
- Format scores computed independently per player and format: proxy score, z-score within that format's eligible pool. Format statuses: `ELIGIBLE`, `OBSERVED_NOT_ELIGIBLE`, `NOT_OBSERVED`.
- Combined: exists only if both formats are `ELIGIBLE`; `combined = w_ipl * z_ipl + w_t20i * z_t20i`. Otherwise `combined` is NULL and `combined_status` is `SINGLE_FORMAT_IPL_ONLY`, `SINGLE_FORMAT_T20I_ONLY` or `NO_VALID_FORMAT` (and `BOTH_FORMATS_VALID` when computed). Never zero-filled, never imputed. Degenerate configs: 100:0 and 0:100 keep the same combined population (both formats valid), so their ranks equal the IPL or T20I z-score ranks within that population, documented; eligibility is identical across all eight configs and the report shows that, plus the counts of single-format players excluded from the combined list.
- Single-format players appear in their own format ranking and are excluded from the combined ranking with a note. Optional `adjusted_estimate` (the available format's z-score, weights renormalised to the available format) is a separate column and section labelled ADJUSTED_ESTIMATE, not used in the default combined ranking.
- For each config and role: combined ranking; Top 10 overlap and Spearman versus default 70:30 and the full 8x8 pairwise matrices (n stated); movement versus default; entering and leaving the Top 10; biggest movers. Every ranking row carries `config_id, config_version, ipl_weight, t20i_weight, config_hash`; top-level `provenance` has config id/version/hash, `generated_at_utc`, `data_version` (latest DATA_VERSION row in `model_versions` plus source sha256s from `dataset_lineage`), `code_version` (sha256 over the sources of `app/analytics`, `app/validation`), seed (none here). Output is byte-identical across runs except `generated_at_utc`.

### Decision 3 procedure (`app/validation/cricsheet_super_over.py`)

1. Official side: read innings and delivery aggregates (`innings`, `deliveries`, `matches`, `teams`) for every match that has innings >= 3, per innings: batting team name, delivery rows, legal balls, batter runs, charged total (`source_total_runs`), wickets, and per delivery summary lists.
2. Cricsheet side: load `cricsheet_index.parquet` (rebuild when absent), dedupe by Cricsheet match id (keep the sorted list of directories per id; compare the innings summaries of copies and report disagreement; canonical directory priority ipl, it20s, t20s, bbl, cpl, mlc, india, 2026). Read the raw JSON only for mapped matches to get overs lists, `info.outcome` (`eliminator`, `bowl_out`), event, venue, and the actual `super_over` representation (the coder prints and documents one example).
3. Mapping rule: exact `match_date` equals a date in `info.dates`, and normalised team pair equal (`normalise_team`), unique after dedupe. Statuses `MAPPED_UNIQUE`, `MAPPED_AMBIGUOUS`, `NOT_FOUND`. Sanity checks on regulation innings: batting team order, delivery count, total runs, wickets of official innings 1/2 versus the non-super-over innings; plus competition and venue soft checks (T20I needs `team_type` international; IPL needs event name containing "Indian Premier League"). `MAPPING_SANITY_FAILED` makes the case UNCONFIRMED.
4. Classification per official match (pure function `classify_super_over(official, cricsheet_or_none)`): `CONFIRMED_SUPER_OVER` when mapping reliable and Cricsheet has the same number of super_over innings as official innings 3/4 with, per position, the same batting team, delivery count, legal balls, runs and wickets; `CONFLICTING` when mapping reliable and Cricsheet has no super over, a different count or order, or any total disagrees (reason codes list the failing fields); `UNCONFIRMED` when mapping is NOT_FOUND, AMBIGUOUS or failed sanity, or the Cricsheet file has no ball data. Supporting columns: outcome keys, official `result_status`/result text.
5. Converse report: among official matches that map reliably, those where Cricsheet has super_over innings and official has no innings 3/4 (report only, using the index, all linkable matches).
6. Outputs: per-match evidence tables (official vs Cricsheet innings side by side), proposed `innings_role_status` values (`CONFIRMED_SUPER_OVER_BY_CRICSHEET`, `UNCONFIRMED_INNINGS_3_4`, `CONFLICT_INNINGS_3_4`) written to the JSON only, plus what remains unverifiable and the Phase 3 rule: innings 3/4 excluded from regulation-pressure metrics by a per-metric restriction. No DB write, no relabel, no `validation_` DB table; the artifact is a JSON file.
